A TRUSTED EXECUTION MODEL FOR CONVERSATIONAL BANKING

AI understands and prepares.
Deterministic systems execute.

One customer request becomes one durable workflow with N work items. Policy controls access, the customer confirms each financial action, and bank systems remain authoritative.

THE CORE PRINCIPLENatural-language messages go through the Orchestrator. Structured UI actions go directly to deterministic services and the existing Request Workflow.

01 / PLATFORM OVERVIEW

One controlled path from conversation to bank outcome

Preparation, consent, durable orchestration and commit execution are separate responsibilities. Every arrow has an explicit caller and executor; the workflow and bank own distinct authoritative state.

BANK SYSTEMS REMAIN AUTHORITATIVE
01 · PLAN

Understand the request

Conversation Manager → Central Orchestrator → pre-agent Policy Service.

02 · PREPARE

Build one durable plan

One Request Workflow coordinates N work items and their dependencies.

03 · CONFIRM

Bind customer consent

Confirmation Service binds every financial approval to its validated payload hash.

04 · EXECUTE

Commit deterministically

Transaction Worker calls Commit Gateway; the mock Bank API owns final status.

02 / COMPONENT RESPONSIBILITIES

Explicit responsibilities and authority

Logical boundaries remain visible even when the prototype runs in one process.

Conversation Manager

Owns conversation state and customer-facing status projection. Calls the Orchestrator for natural language; listens to workflow events and builds channel-neutral responses.

CALLS · Central Orchestrator · SSE projection

Central Orchestrator

Identifies candidate intents, proposes a dependency graph, evaluates pre-agent policy, applies the decision, and starts exactly one Request Workflow.

CALLS · Policy Service · Workflow Access Service

Policy Service

Returns PERMIT, DENY or obligations. It does not invoke agents and does not start or resume workflows.

AUTHORITY · Decision point only

Request Workflow

Owns durable request and work-item state, dependencies, idempotency and unknown-outcome reconciliation. Waits durably for consent.

AUTHORITY · Request and work-item state

Specialist Agent

Receives one scoped preparation task, resolves parameters and returns typed prepared work. It finishes before consent is requested.

ALLOWED · Read + Prepare / Validate only

Confirmation Service

Creates challenge, validates ownership/expiry/payload hash and simulated approval evidence, then records consent. It never executes transactions.

AUTHORITY · Immutable Confirmation Record

Transaction Worker

Deterministic application code verifies policy, consent, hash and dependencies, then calls the Commit Gateway with a stable idempotency key.

ALLOWED · Commit Gateway execution identity

Bank API / System of Record

Validates and posts financial operations. Owns the authoritative status and reference and exposes status reconciliation.

AUTHORITY · Balance, posting, final status
03 / REQUEST AND WORKFLOW MODEL

One request, one workflow, three independent work items

A workflow coordinates parallel preparation and explicit dependencies; it is never split into one workflow per intent.

06 / CONSENT APPROVAL AND WORKFLOW RESUME

Structured action bypasses the Orchestrator

Confirmation Service verifies the exact challenge, then signals the existing workflow. A deterministic worker—not an agent—calls commit.
